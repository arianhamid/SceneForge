# ۸. چگونه پروژه را توسعه دهیم

این فایل خلاصه‌ی فارسیِ راهنمای کامل انگلیسی [`docs/guides/ADDING_A_PROVIDER.md`](../guides/ADDING_A_PROVIDER.md) است، به‌همراه چند پیشنهاد مشخص برای کاری که همین الان می‌توانی روی آن کار کنی.

## راهنمای گام‌به‌گام: اضافه‌کردن یک Provider جدید

### قدم ۱: آیا قابلیت مورد نظرت از قبل تعریف شده؟

فایل `sceneforge/core/capability.py` را نگاه کن. اگر قابلیتی که می‌خواهی پیاده‌سازی کنی از قبل آن‌جا هست (مثلاً `CAPTION` یا `OBJECT_DETECTION`)، برو قدم بعد. اگر نه، باید آن را به `Capability` اضافه کنی و در `sceneforge/core/capability_registry.py` مشخص کنی با کدام نوع `Media` سازگار است.

### قدم ۲: نوع Provider را انتخاب کن

| نوع کارت... | از این کپی کن | نیاز به تزریق مدل؟ |
|---|---|---|
| یک ابزار خط‌فرمان (مثل ffmpeg) | `sceneforge.contrib.ffmpeg` | خیر |
| یک الگوریتم بدون وزن مدل (مثل scenedetect) | `sceneforge.contrib.scenedetect` | خیر |
| یک مدل با وزن‌های همراه پکیج (مثل OpenCV، Tesseract) | `sceneforge.contrib.opencv` یا `sceneforge.contrib.tesseract` | خیر |
| یک مدل با وزن‌های دانلودی (مثل Whisper) | `sceneforge.contrib.whisper` | **بله** |

**نکته‌ی خیلی مهم:** قبل از فرض کردن که به تزریق نیاز داری، چک کن که آیا کتابخانه‌ی موردنظرت وزن‌هایش را همراه خودش نصب می‌کند یا نه (مثل OpenCV و Tesseract) یا واقعاً باید چیزی از اینترنت دانلود کند (مثل Whisper).

### قدم ۳: اگر به مدل نیاز داری، آن را «تزریق» کن، نسازش

```python
from typing import Protocol, runtime_checkable

@runtime_checkable
class MyModelProtocol(Protocol):
    def infer(self, input_path: str) -> MyModelOutput: ...

class MyProvider(Provider):
    def __init__(self, model: MyModelProtocol) -> None:
        self._model = model
```

این کار به تو اجازه می‌دهد بدون نیاز به مدل واقعی، منطق Provider را تست کنی (با یک مدل ساختگی که همان شکل را دارد).

### قدم ۴: Artifact را بنویس

```python
@register_artifact_type
@dataclass(frozen=True, slots=True)
class MyArtifact(Artifact[PayloadType]):
    media_id: UUID = field(default_factory=uuid4)
    kind: ArtifactKind = ArtifactKind.SOMETHING
    category: ArtifactCategory = ArtifactCategory.ANALYSIS  # یا DETECTION، RECOGNITION، DERIVED
    provider: str = "my_provider"
```

### قدم ۵: Provider را بنویس

قوانینی که همیشه باید رعایت کنی (همه‌ی پنج Provider واقعی از این پیروی می‌کنند):

- اگر نوع `Media` ورودی اشتباه است، بلافاصله `TypeError` بده.
- هیچ‌وقت خطای یک کتابخانه‌ی بیرونی را مستقیم پرتاب نکن؛ همیشه در `ProviderError` بپیچ (با `from exc`).
- `version` را هر بار که منطق داخلی تغییر کند، عوض کن (چون بخشی از کلید کش است).
- اگر Provider تو یک قاب استخراج‌شده را پردازش می‌کند، مسیر فایل را در فیلدی مثل `source_frame_path` نگه دار — این‌طوری بعداً یک Knowledge Builder می‌تواند بدون نیاز به `media_id` یکسان، آن را به صحنه‌ی درست نسبت دهد.

### قدم ۶: تست بنویس

حداقل این‌ها را داشته باش:

- یک تست برای هر حالت شکست (نوع اشتباه، مسیر نامعتبر، خطای کتابخانه‌ی بیرونی).
- یک تست برای مسیر موفق با مقادیر واقعی.
- اگر مدل‌محور است: تست‌های واحد با مدل ساختگی + یک تست کوچک که فقط چک می‌کند شکل کتابخانه‌ی واقعی با Protocol تو سازگار است (بدون اجرای واقعی مدل).
- اگر ابزار/الگوریتمت رایگان قابل‌اجراست (بدون وزن، بدون اینترنت): یک تست یکپارچگی **واقعی** با فایل واقعی — نه فقط شبیه‌سازی‌شده.

### قدم ۷: مستندات را به‌روزرسانی کن

- `docs/specifications/PROVIDER_SPEC.md` — Provider جدیدت را به لیست اضافه کن.
- `docs/architecture/DOMAIN_MODEL.md` — اگر مربوط به «نردبان درک» است.
- `pyproject.toml` — اگر پکیج بیرونی نیاز دارد، یک extra جدید اضافه کن.
- `.ai/PROJECT_STATE.md` و `.ai/NEXT_TASK.md` — وضعیت واقعی پروژه را به‌روز نگه دار.

## اشتباهات رایجی که قبلاً در این پروژه دیده و اصلاح شده‌اند

- ساختن یک مدل یا اتصال شبکه داخل `__init__`، به‌جای تزریق آن.
- اضافه‌کردن یک متغیر سراسری (global) «فقط برای این‌بار» — همیشه به یک باگ واقعی تبدیل می‌شود.
- اجازه دادن به یک Provider که `Media` ورودی‌اش را تغییر دهد — اگر Provider تو چیزی کشف می‌کند که باید خودِ `Media` را اصلاح کند (نه فقط یک Artifact جدید بسازد)، آن یک `MediaEnricher` است، نه یک `Provider`.
- نوشتن مستندات درباره‌ی چیزی که هنوز پیاده‌سازی نشده، به‌شکلی که انگار پیاده‌سازی شده.

## پیشنهادهایی برای کاری که می‌توانی همین الان شروع کنی

با توجه به وضعیت واقعی پروژه (که در `.ai/NEXT_TASK.md` همیشه به‌روز است)، این‌ها نقاط خوبی برای یادگیری عملی هستند:

### ۱. یک Provider برای `CAPTION` یا `OBJECT_DETECTION`

این دقیقاً همان چیزی است که پروژه را به لایه‌ی «حقایق» (Facts) نزدیک می‌کند. یک مدل توضیح‌دهنده‌ی تصویر (Image Captioning VLM) معمولاً وزن‌هایش را باید دانلود کند — پس این فرصت خوبی است تا الگوی «تزریق وابستگی» (قدم ۳ بالا) را با دست خودت تمرین کنی، دقیقاً مثل `WhisperTranscribeProvider`.

### ۲. یک Knowledge Builder برای متن روی صفحه

`SceneTextBuilder` الان فقط متن را جمع‌آوری می‌کند. یک قدم منطقی بعدی (اما با احتیاط، طبق اصل «قبل از رسمی‌کردن، اثبات کن») این است که ببینی آیا واقعاً یک نیاز واقعی برای طبقه‌بندی این متن‌ها (مثلاً «این یک تابلوی خیابان است» در مقابل «این زیرنویس است») وجود دارد یا نه.

### ۳. خواندن فایل‌های تست به‌عنوان مستندات زنده

بهترین راه برای یادگیری این‌که یک قطعه‌کد چطور *باید* استفاده شود، خواندن تست‌های واقعی‌اش است. مثلاً `tests/knowledge/test_scene_text_integration.py` نشان می‌دهد چطور یک متن واقعی داخل یک ویدیوی واقعی (با فیلتر `drawtext` در ffmpeg) ساخته می‌شود و بعد با OCR واقعی خوانده می‌شود.

### ۴. خواندن سوابق تصمیمات معماری (ADR)

فایل [`10-decision-log.md`](10-decision-log.md) خلاصه‌ی فارسی هر ۲۲ تصمیم را دارد. این بهترین راه برای فهمیدن *چرا* پروژه این‌شکلی است، نه فقط *چه‌شکلی* است.
